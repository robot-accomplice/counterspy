# Phase 2.5 — Streaming messages, and merging Intercept into Exfiltration

**Status:** REVISED after adversarial swarm review (2026-07-17). The review invalidated §3.1's original
mechanism; the redesign below needs sign-off before planning. §6 decisions stand — the review attacked
their consequences, not the decisions.
**Predecessor:** `2026-07-15-phase2-tls-interception-design.md` (shipped; verified live 2026-07-16).

## 0. What the review changed

The first draft of this spec proposed parsing each direction independently and pairing
request+response into one event. **That does not work**, and two reviewers found it independently:

- A response cannot be framed without its **request** (`HEAD` carries `Content-Length` but no body;
  `204`/`304` have no body). Parsing directions independently mis-frames, and one mis-frame desyncs a
  keep-alive connection permanently.
- `relay()` copies the two directions in **separate goroutines** with nothing correlating them, so
  "pair the request with its response" was not derivable from the design as written.

The review also found a **live secret leak in shipped code** (not a spec flaw) — fixed in `419d421`
before this revision; recorded in §1.4 because §6.2 depends on it.

## 1. Why

Phase 2 works — it decrypts real traffic, attributes it to apps, and reverts cleanly. Live use and
review exposed four faults.

**1.1 The capture is truncated and the UI implied it wasn't.** The proxy keeps `FlowCaptureBytes` (8 KB)
per direction in a `capBuf` and publishes one record at connection close. A real session captured a
26,836-byte Sentry POST from Proton Mail — ~70% never recorded. The view then capped the *display* at 8
lines and printed `… (5 more lines)`, implying content that did not exist. The display cap is fixed
(`9952a6c`); the **capture** cap remains, and buffer-then-truncate is the wrong shape.

**1.2 Flows are stamped at open, published at close.** Keep-alive connections surface after shorter ones
that started later (`14:44:58` printed above `14:44:28`). The viewer sorts by `At` to compensate — a
workaround for a record shape that does not match reality.

**1.3 Intercepted and Exfiltration are the same thing.** Exfiltration asks *"this app is trusted; what is
it sending?"* and its inspector answers with content until it hits `ENCRYPTED (TLS) — metadata only`.
Intercept removes that wall; it does not ask a new question. The split produced a duplicate per-app
rollup beside a per-app rollup, and the Intercepted view was rebuilt four times because the split was
accepted rather than questioned.

**1.4 Bounded capture defeated masking (FIXED, `419d421`).** `reBodySecret`'s value alternation required
a closing quote, so a body cut mid-value (`"api_key":"sk_live_ABC`) matched neither branch and published
the partial secret **in the clear**. Reproduced against the live pipeline. Fixed by adding the dangling
open-quote case, mirroring `rePEMOpen`. **This is a precondition for §6.2**: any design that publishes
partial text must assume truncation lands mid-token, and the masking rules must survive it.

## 2. Approved decisions (unchanged)

| Decision | Choice |
|---|---|
| Streaming granularity | **Per HTTP message** |
| Console shape | **Merge into Exfiltration**; no separate Intercepted screen |
| Daemon | Encourage on foreground runs; prompt at install |
| Boot ordering | *"armed before your session starts"* — never "first" (§5.2) |

## 3. Design (revised)

### 3.1 Per-message streaming

The relay stays a **byte-for-byte mirror**: bytes are forwarded verbatim, and a *copy* is parsed. We do
NOT become a re-serialising HTTP proxy — that would change what the server sees and break the read-only
invariant.

**3.1.1 Framing requires request↔response correlation.** The two parse goroutines share a **request
queue**: the request parser pushes `{method, exchangeID}` as each request completes; the response parser
pops it to frame the response correctly (`HEAD` → no body regardless of `Content-Length`; `204`/`304` →
no body; `1xx` informational → does not consume a queue entry). This is mandatory, not an optimisation:
without it, `HEAD` alone desyncs the connection forever.

**3.1.2 The pump needs its OWN framing reader.** `inspect.readBody` must **not** be reused: it is a
one-shot *preview* reader (`io.ReadAll(io.LimitReader(body, maxRawBody))` then `Close()`) that never
drains the remainder — reusing it guarantees the permanent desync above. The pump's reader must separate
*how much to keep* (bounded, for display) from *how much to skip* (all of it, to stay framed):
- `Content-Length`: keep min(N, cap), skip the rest by count.
- `chunked`: walk chunk headers, keep bounded payload, skip the rest.
This is what makes §6.2's "publish a partial and keep framing" achievable at all.

**3.1.3 Desync ⇒ opaque, once.** Any framing failure — an unparseable message, a protocol upgrade
(`101`), a queue mismatch, anything that stops being HTTP/1.1 — resolves to §6.2's second branch: mark
the connection `opaque` **once** (§6.3), stop parsing, keep relaying. There is no "resync after garbage"
path; attempting one would publish fabricated messages, which is worse than admitting we lost framing.

**3.1.4 Events are PER DIRECTION, not paired.** *(Change from the first draft — needs sign-off.)* A
paired request+response event must wait for the response, which (a) delays showing a request whose
response is slow or never arrives, and (b) re-introduces §1.2's ordering bug at message granularity when
a response completes before a slow-uploading request. Instead each direction publishes when **it**
completes, carrying `ExchangeID` (connection ID + sequence) so the viewer groups them for display. A
request that never gets a response still appears — honestly, as a request with no response.

**3.1.5 Bounds.** Per-message is not unbounded:
- `MaxMessageBytes` (proposal: 1 MB) and `MaxMessageAge` (proposal: 30s) bound one message; on either,
  publish what was captured marked `partial`, then **continue framing** via 3.1.2's skip path.
- **The header block is bounded by Go, not by us.** `net/textproto`'s MIME header reader applies its own
  ceiling *before* any application cap, so a hostile header block can spike memory past `MaxMessageBytes`.
  The pump must impose its own header-size limit rather than assume `MaxMessageBytes` covers it.
- **Decoded size is already bounded** and must stay so: `decodeBody`'s `io.LimitReader(r, maxBodyPreview+1)`
  caps *decoded* output regardless of input, so compression bombs are handled today. Do not regress this.

**3.1.6 Model shape.**

```
InterceptedMessage {
  SchemaVersion int     // REQUIRED — see 3.1.7
  ExchangeID    string  // connection id + sequence; the viewer groups req/resp by this
  Direction     string  // request | response
  At            string  // when THIS message completed
  PID           int
  App           string
  DestName, DestIP, SNI string
  Status        string  // decrypted | pinned | opaque | error (closed set, unchanged)
  Text          string  // decoded + masked; "" for non-decrypted statuses
  Bytes         int     // TRUE wire bytes for this message
  State         string  // complete | partial | streaming   <- NOT a bool (see below)
}
```

`State` replaces the first draft's `Truncated bool`, which conflated two different facts a reader must
distinguish: **`partial`** = this is all you will ever get for this message; **`streaming`** = bounded
for now, more events are coming for this exchange.

`pinned` / `opaque` / `error` remain **per-connection** facts published exactly once (§6.3), with no
`Direction`/`Text`.

**3.1.7 The wire format must be versioned.** `json.Unmarshal` silently ignores unknown fields and leaves
missing ones zero — so an OLD log record read by NEW code parses without error into an *empty but
apparently complete* `decrypted` message. That is the §1.1 sin (implying content we do not have) served
by the reader instead of the writer. `SchemaVersion` is required; a record without the current version
is rejected **loudly**, not best-effort parsed.

### 3.2 Merge into Exfiltration

**The merge point is the inspector's verdict, not a tab.** With a live daemon, `ENCRYPTED (TLS) —
metadata only` gains an answer.

- **Exfiltration rows** unchanged (nettop/lsof rollup per app — already the right axis).
- **Inspect (`i`)**: if the intercept stream has messages for that app + destination, render them
  (decrypted, masked, time-ordered, with the dividers, honest non-decrypted reasons and truncation
  notices already built). Otherwise the existing bpf verdict, unchanged.
- **Honest empty state:** `No live intercept daemon found. Showing only unencrypted traffic.`
- **Sudo prominence:** make the existing startup warning prominent; re-state on entering Exfiltration:
  `No traffic found — is the intercept daemon running as sudo?`
- **Single ingestion point (required).** The per-app message buffer the inspector queries MUST be fed
  *only* through the sanitise-gated read path (`ReadSocket` → `scanFlows` → `sanitizeFlow`). The socket is
  untrusted input (anyone who can write it). Since §3.1.6 forces `sanitizeFlow` to be rewritten anyway,
  there is real risk a new aggregator is written against the raw wire type and quietly bypasses the
  boundary. Name the one ingestion function in the plan.

**Deleted:** `internal/tui/interceptmodel.go`, `interceptview.go`, `interceptrun.go` + tests;
`runInterceptTUI`. The rendering (dividers, honest reasons, truncation notices) **moves** to the
inspector — the work is kept, only its duplicate host goes.

**Decoupling invariant holds:** `tui` imports only `model` + `mark`; the socket read stays in `main` and
feeds the view over a channel, as `Sampler`/`Inspector` do.

### 3.3 Daemon nudges

- A foreground `intercept` run suggests `--install-daemon`, framed by what it buys: login/startup
  phone-home is not missed because it is undecryptable — it already happened before you could arm.
- `install.sh` offers the daemon at install time.
- Wording: `armed before your session starts`. Never "first" (§5.2).

## 4. What this does NOT change

Read-only mirror (redact/block is Phase 3); cooperative coverage (evasive software still needs the
NetworkExtension proxy); consent, teardown, and the arm⇒disarm invariant; the closed honest status set.

## 5. Known behaviours recorded honestly

**5.1 We silently downgrade HTTP/2 → HTTP/1.1.** No `NextProtos` is set on either TLS config, so no ALPN
is offered and clients fall back to HTTP/1.1. Verified: live captures show `HTTP/1.1` from WhatsApp and
Proton, apps that otherwise negotiate h2. Consequences: it is why per-message framing is feasible at all;
it contradicts "byte-for-byte **unmodified**" in spirit (the payload is unmodified, the negotiation is
not) and the package doc must say so; **and a client that requires h2 may hard-fail rather than downgrade
— gRPC-over-TLS is the likely case. Unmeasured. The whole framing design rests on this property, so it
should be measured, not assumed.**

**5.2 launchd has no ordering primitive.** `man launchd.plist`: jobs *"are evaluated completely
independently by the system."* No `Before`/`After`. A system LaunchDaemon does start before any user logs
in — covering user-session apps — but concurrent system daemons are a race we cannot win.

**5.3 `br` is NOT decoded.** `decodeBody` handles `gzip` and `deflate` only. The first draft of this spec
claimed `br` — wrong, and the evidence was already on screen: a live capture showed `Content-Encoding: br`
*without* the `(decoded)` marker, directly beside `gzip (decoded)`. Under per-message streaming this gap
surfaces on **every** brotli exchange rather than once per connection, so it is now a visible product
defect. Either add brotli or state plainly in the UI that the body is undecoded — silently showing
compressed bytes as "content" is the §1.1 sin again.

**5.4 Two truncation layers existed and only one was surfaced.** Recorded so no future reader
re-introduces a bounded buffer without a matching honest notice.

## 6. Resolved (maintainer, 2026-07-17)

**6.1 `console --intercept` is DELETED.** Not kept as a log reader — removed entirely. `--intercept`,
`runInterceptView`, `formatFlow`, the stdout tail, the socket/log dispatch and their tests all go.
`publish.ReadLog` loses its only caller and must be deleted with them or it becomes dead code for the
third time (an unwired `ReadLog`, an unpopulated `PID`).

> **Two gaps this creates, for the plan to close — not a re-litigation:**
> 1. The daemon's rotating `--log` — the daemon's entire justification — then has **no reader in the
>    product**. Either Exfiltration reads the log when no live socket exists, or the log is `jq`-only and
>    we say so.
> 2. Deleting `ReadLog` deletes `TestLogSink_ReadBack`, the **only** test exercising the log
>    write→read-through-sanitise round trip (it also asserts an untrusted `Status: "BOGUS"` is coerced).
>    `TestLogSink_RotatesAndKeeps` is `os.Stat`-only and does not cover it. The plan must rebuild an
>    equivalent test against the internal scan path, or decrypted traffic sits at 0600 on disk with
>    neither a consumer nor a test proving its write path stays sane.

**6.2 Never-completing responses: BOTH — terminate if we can, else opaque.** Bound and publish a partial
where still framable (§3.1.5), continue via the skip path; where framing is impossible (§3.1.3), mark
`opaque` and relay on.

**6.3 Opaque publishes ONCE per connection. Never repeated.** No periodic "still opaque", no byte-count
refreshes, no close event restating it. A long-lived opaque connection must not become a heartbeat.

**6.4 Attribution is per CONNECTION, reused by every message on it.** `portOwner` already runs once per
connection; per-message lookups would fork lsof at message rate.

## 6a. Open questions raised by the review

**6a.1 The pre-upgrade exchange on a websocket/h2c connection.** It IS fully framable and frequently
carries `Authorization`/cookie auth. Do we publish it as a normal `decrypted` message *before* marking the
connection `opaque`? Doing so contradicts "one status per connection" (§6.3); not doing so silently
discards a legitimately readable, credential-bearing exchange. **Proposal:** publish the exchange
(`decrypted`), then publish `opaque` once at the upgrade — the connection's status *changes*, and §6.3's
"once" means "no repeats", not "never a transition". Needs sign-off.

**6a.2 Mid-stream errors on a decrypted connection.** After N good messages the relay/parser may error —
not a clean close, not an upgrade. Nothing is specified. Today's pump publishes `FlowError` rather than
dropping silently (`proxy.go` handles an unresolved CONNECT that way). **Proposal:** publish one terminal
`error` event for the connection. Needs sign-off.

**6a.3 `sanitizeFlow` never caps `App`.** Pre-existing (an untrusted producer's process name is unbounded
until `model.Clean` at draw). Not caused by this spec, but §3.1.6 forces the bounds to be re-derived —
close it there.

## 7. Testing strategy

- **Framing:** a keep-alive connection with N pipelined exchanges publishes 2N direction-events in
  completion order. **`HEAD` must not desync** (the canonical case: `Content-Length` present, no body).
  `204`/`304` likewise. `100-continue`/`103` must not consume a queue entry.
- **Desync ⇒ opaque:** deliberately corrupt framing mid-connection → exactly one `opaque`, no fabricated
  messages, relay continues.
- **Bounds:** a >1 MB message publishes `partial` **and the connection stays framed** (the next message
  parses correctly — this is what proves 3.1.2's skip path). A never-completing response publishes
  `streaming` rather than buffering forever or vanishing. A hostile header block does not blow memory.
- **Masking under truncation (mandatory):** a secret cut mid-token at the `partial` boundary is still
  masked — the §1.4 regression, now a permanent test. Also the chunk-spanning secret this design buys.
- **Schema:** an old-format record is rejected loudly, not parsed into an empty `decrypted` message.
- **Merge:** inspect renders decrypted messages with a live stream; without one, the bpf verdict and the
  honest empty state. Decoupling invariant still passes. The inspector's buffer is fed only via the
  sanitise-gated path.
- **Regression:** `pinned`/`opaque`/`error` still publish exactly once per connection, never silently.
- Gate: `-race` ×2, both builds, `architext validate`, coverage ≥ 80%.

## 8. Risks

- **Masking regression is the top risk**, and §1.4 proved it is not theoretical: bounded capture already
  defeated the body-secret rule once, in shipped code. Every partial-publish path must mask what it has,
  and the truncation-boundary test is mandatory, not optional.
- **Framing complexity is the second.** The correlation queue + custom skip reader is real HTTP-proxy
  machinery replacing a byte sniffer. The mitigation is that every failure has one honest destination
  (`opaque`, once) rather than a resync heuristic.
- **Wire-format churn:** socket, rotating log, reader and `sanitizeFlow` all change; old logs must be
  rejected loudly (§3.1.7).
- **Scope creep into Exfiltration:** the merge touches a large working subsystem. Keep it to the inspector
  + empty states; do not redesign a view that works.
- **This reworks shipped, verified code.** v0.7.0 is cuttable today. Phase 2.5 lands on its own branch off
  `develop` **after** that cut, not by holding the release open.
