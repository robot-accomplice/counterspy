# Phase 2.5 — Streaming messages, and merging Intercept into Exfiltration

**Status:** approved (2026-07-17); §6 resolved by the maintainer. Pending an adversarial swarm review before planning.
**Predecessor:** `2026-07-15-phase2-tls-interception-design.md` (shipped; verified live 2026-07-16).

## 1. Why

Phase 2 works — it decrypts real traffic, attributes it to apps, and reverts cleanly. Live use exposed
three faults, two of which are design errors rather than bugs.

**1.1 The capture is truncated and the UI implied it wasn't.** The proxy keeps `FlowCaptureBytes`
(8 KB) per direction in a `capBuf` and publishes one record when the connection closes. A real session
captured a 26,836-byte Sentry POST from Proton Mail — ~70% of it was never recorded. The view then
capped the *display* at 8 lines and printed `… (5 more lines)`, implying content that did not exist and
could not be reached by any key. Implying content we don't have is the one thing this tool exists not to
do; it is why a pinned flow says "bypassed, not decrypted" instead of showing nothing. The display cap
is already fixed (commit `9952a6c` shows the full capture and states truncation honestly), but the
**capture** cap remains, and buffering-then-truncating is the wrong shape.

**1.2 Flows are stamped at open and published at close.** A keep-alive connection therefore surfaces
long after shorter connections that started later — real output showed `14:44:58` printed above
`14:44:28`. The viewer now sorts by `At` to compensate, which is a workaround for a record shape that
does not match reality: one long-lived connection is not one event.

**1.3 Intercepted and Exfiltration are the same thing.** Exfiltration asks *"this app is trusted; what
is it sending, where, how much?"* and its inspector answers with content — until it hits TLS and reports
`ENCRYPTED (TLS) — metadata only`. Intercept does not ask a new question; it removes that wall. Treating
it as a separate view produced a duplicate: a per-app rollup with a running log, sitting beside a per-app
rollup with a running log. The Intercepted view was rebuilt four times because the split was accepted as
given rather than questioned.

## 2. Approved decisions

| Decision | Choice |
|---|---|
| Streaming granularity | **Per HTTP message** — decode + redact a complete request/response, publish, continue |
| Console shape | **Merge into Exfiltration.** Decryption enriches the existing view; no separate Intercepted screen |
| Daemon | Encourage it on foreground runs; prompt at install |
| Boot ordering | Framed as *"armed before your session starts"* — **not** "first" (see §5.2) |

## 3. Design

### 3.1 Per-message streaming

**Replace** the per-connection `capBuf` + single publish with per-message events.

The relay stays a byte-for-byte mirror. Alongside it, each direction is parsed as an HTTP/1.1 message
stream (`http.ReadRequest` / `http.ReadResponse` over the tee'd bytes). When a **complete** message is
framed, it is decoded (`DecodeCleartext`: dechunk + gzip/deflate/br) and `Redact`ed, published as an
event, and the parser continues on the same connection.

**Why per-message and not raw chunks.** Redaction is the guarantee everything else rests on
(`Authorization: [redacted]` in live output). A secret can straddle a raw chunk boundary, so per-chunk
masking would leak its tail; an overlap window is a heuristic that fails on long or oddly-encoded
secrets. A message is a natural boundary that no secret crosses, so masking stays exactly as correct as
it is today while the 8 KB cap disappears.

**What this fixes for free:** the ordering bug (each message is stamped when it *completes*, and
published then — so publish order is timeline order); keep-alive connections emit many events instead of
one truncated summary; and `FlowCaptureBytes` is deleted rather than raised.

**Bounds — still required, but honest.** Per-message does not mean unbounded:
- A single message exceeding `MaxMessageBytes` (proposal: 1 MB) publishes what was captured **plus an
  explicit truncation notice**, reusing the honest wording already shipped in `9952a6c`.
- A response that never completes (SSE, chunked-forever, websocket upgrade) must not buffer forever nor
  vanish. Proposal: publish an event marked `streaming` after `MaxMessageAge` (proposal: 30s) or
  `MaxMessageBytes`, whichever first, and continue. **Open question 6.2.**
- Non-HTTP payloads inside TLS cannot be framed. Today they land as `opaque`. That must not regress into
  silence. **Open question 6.3.**

**Model change.** `model.InterceptedFlow` (per-connection) becomes a per-message event. Proposed shape —
one event per request/response **exchange**, because that is the unit a reader reasons about and how the
log already renders (`→` / `←`):

```
InterceptedMessage {
  At        string  // when the exchange COMPLETED (publish order == timeline order)
  PID       int
  App       string
  DestName  string  // CONNECT authority
  DestIP    string
  SNI       string
  Status    string  // decrypted | pinned | opaque | error  (unchanged, closed set)
  Request   string  // decoded + masked; "" for non-decrypted statuses
  Response  string
  ReqBytes  int     // TRUE wire bytes for this message
  RespBytes int
  Truncated bool    // this message exceeded MaxMessageBytes / MaxMessageAge
}
```

`pinned` / `opaque` / `error` remain **per-connection** facts (there is no message to report), so they
publish exactly once per connection, as now. Only `decrypted` connections emit multiple events.

**Blast radius:** `internal/intercept/proxy.go` (the pump), `internal/model/interceptflow.go` (wire
format), `internal/intercept/publish/*` (socket + rotating log + `sanitizeFlow` bounds), the log reader,
and every consumer. This is the reason streaming lands **before** the merge — the merge consumes this
shape.

### 3.2 Merge into Exfiltration

**The merge point is the inspector's verdict, not a tab.** `internal/inspect` today returns an honest
coverage verdict: readable plaintext / TLS ciphertext (metadata only) / cleartext binary. With a live
intercept daemon, the "TLS ciphertext" case has an answer.

- **Exfiltration rows** are unchanged (nettop/lsof rollup per app — already the right axis).
- **Inspect (`i`)** on a flow: if the intercept stream has messages for that app + destination, render
  them (decrypted, masked, time-ordered, with the packet dividers and truncation notices already built).
  Otherwise, the existing bpf verdict, unchanged.
- **Honest empty state**, per the maintainer's wording:
  `No live intercept daemon found. Showing only unencrypted traffic.`
- **Sudo prominence.** A startup sudo warning exists but is easy to miss; make it prominent, and
  re-state it on entering Exfiltration: `No traffic found — is the intercept daemon running as sudo?`

**Deleted:** `internal/tui/interceptmodel.go`, `interceptview.go`, `interceptrun.go` and their tests;
`runInterceptTUI`; the second keymap. The per-app running log's *rendering* (dividers, honest
non-decrypted reasons, truncation notices) is **kept** and moves into the inspector — the work is not
lost, only its duplicate host.

**Decoupling invariant holds:** `tui` still imports only `model` + `mark`; the socket read stays in
`main` and feeds the view over a channel, exactly as `Sampler`/`Inspector` do today.

### 3.3 Daemon nudges

- A foreground `intercept` run that exits suggests `--install-daemon`, framed by what it buys: traffic
  that happens **before you can arm** — login/startup phone-home — is not currently missed because it is
  undecryptable, but because it already happened.
- `install.sh` offers the daemon at install time.
- Wording is `armed before your session starts`. Never "first" (§5.2).

## 4. What this does NOT change

- Read-only mirror: bytes are still relayed unmodified; redact/block remains Phase 3.
- Cooperative coverage: apps ignoring the system proxy are still unseen; that needs the
  NetworkExtension transparent proxy (on the roadmap).
- Consent, teardown, and the arm⇒disarm invariant for the foreground mode.
- The closed, honest status set.

## 5. Known behaviours to record honestly

**5.1 We silently downgrade HTTP/2 → HTTP/1.1.** The proxy sets no `NextProtos` on either TLS config, so
no ALPN is offered and clients fall back to HTTP/1.1. This is *verified*, not theorised: live captures
show `HTTP/1.1` from WhatsApp (`api.whatsapp.net`) and Proton (`mail-api.proton.me`) — apps that
otherwise negotiate h2. Consequences:
- It is why per-message HTTP framing is feasible at all (everything through us is h1).
- It contradicts, in spirit, "relays byte-for-byte **unmodified**" — the *payload* is unmodified, the
  *protocol negotiation* is not. The package doc must say so.
- An app that requires h2 may behave differently or fail through the proxy. Unmeasured.

**5.2 launchd has no ordering primitive.** `man launchd.plist`: jobs *"are evaluated completely
independently by the system."* There is no `Before`/`After`. A system LaunchDaemon does start before any
user logs in — which covers user-session apps (the ones that matter here) — but concurrent system
daemons are a race we cannot win. Do not promise "first".

**5.3 Two truncation layers existed and only one was surfaced.** Recorded so the next reader does not
re-introduce a bounded buffer without a matching honest notice.

## 6. Resolved (maintainer, 2026-07-17)

**6.1 `console --intercept` is DELETED.** Not kept as a log reader — removed entirely. Exfiltration is
the one place decrypted traffic is read. The `--intercept` flag, `runInterceptView`, `formatFlow`, the
stdout tail, the socket/log dispatch and their tests all go. `publish.ReadLog` loses its only caller and
must be deleted with them, or it becomes dead code again — the exact defect this project has already hit
twice (an unwired `ReadLog`, an unpopulated `PID`).

> Consequence to face in planning: the rotating `--log` (which the DAEMON writes, and which is the
> daemon's entire justification — "what did my machine send overnight?") then has **no reader in the
> product**. Either Exfiltration reads the log when no live socket exists, or the log is only readable
> by external tools (`jq`). This is not re-litigating 6.1; it is a gap 6.1 creates that the plan must
> close. Flagged for the spec review.

**6.2 Never-completing responses: BOTH — terminate if we can, else opaque.**
- Where the stream is still HTTP-framable, bound it: at `MaxMessageBytes` (1 MB) or `MaxMessageAge`
  (30s), publish what was captured, explicitly marked partial, and keep framing.
- Where framing is impossible (protocol upgrade: websocket / h2c / anything that stops being HTTP),
  stop trying: mark the connection `opaque` and relay on.

**6.3 Opaque publishes ONCE per connection. Never repeated.** No periodic re-publishing of "this is
still opaque", no byte-count refreshes, no close event restating it. One event at detection, then the
proxy relays in silence. The reader learns the connection exists and cannot be read; saying it again
adds nothing and would drown the log — a long-lived opaque connection must not become a heartbeat.

**6.4 Attribution is per CONNECTION, reused by every message on it.** `portOwner` (lsof snapshot, 2s
TTL) already runs once per connection; per-message events reuse that result. A per-message lookup would
fork lsof at message rate. This is a plan task, not a question — carried here so it is not lost.

## 7. Testing strategy

- **Pump:** a keep-alive connection carrying N pipelined request/response pairs publishes N events, in
  completion order, each fully decoded + masked. A secret spanning a *chunk* boundary is still masked
  (this is the property per-message framing buys — test it explicitly).
- **Bounds:** a >1 MB message publishes with `Truncated` set and the honest notice; a never-completing
  response publishes a partial rather than buffering forever or vanishing.
- **Ordering:** publish order equals completion order without the viewer needing to sort.
- **Merge:** inspect with a live stream renders decrypted messages; without one, the existing bpf verdict
  and the honest empty state. Decoupling invariant test must still pass.
- **Regression:** `pinned` / `opaque` / `error` still publish exactly once per connection, never silently.
- Full gate as always: `-race` (×2), both builds, `architext validate`, coverage ≥ 80%.

## 8. Risks

- **Masking regression is the big one.** Per-message framing preserves today's correctness *only if* the
  message is complete before `Redact` runs. Any path that publishes a partial (§6.2 bounds) must mask
  what it has and be explicit that it is partial. A test for a boundary-spanning secret is mandatory.
- **Wire-format churn.** The socket, rotating log, and log reader all change shape. Old log files become
  unreadable; `sanitizeFlow`'s untrusted-input bounds must be re-derived for the new fields.
- **Scope creep into Exfiltration.** The merge touches a large, working subsystem (`egressmodel`,
  `egressview`, `egresszoom`, `inspect`). The plan must keep it to the inspector + empty states, not a
  redesign of a view that already works.
- **This is a rework of shipped, verified code.** v0.7.0 is complete and cuttable today. Phase 2.5 should
  land on its own branch off `develop` after that cut, not by holding the release open.

## 9. Sequencing

1. Streaming (per-message) — changes the record everything consumes.
2. Merge into Exfiltration — mostly deletion once events flow.
3. Daemon nudges + install prompt.

Each is its own swarm checkpoint with fan-out review; RCA now routes through the `code-rca` skill.
